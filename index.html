    db.keyValueBucket("sessions").put("tok-abc", "user-1");
    db.keyValueBucket("sessions").expire("tok-abc", Duration.ofMinutes(30));
}
Core Capabilities

One engine, four data models

EmbedJNoSQL has exactly one execution engine. Documents, Key-Value, Redis-style structures, and Wide-Column families are data models on top of the same storage substrate — no second engine to configure.

📄
Document Collections
Schemaless JSON documents with native predicates ($eq, $gt, $regex, $exists…), sorting, pagination, TTL, runtime secondary indexes, and dotted-path queries into nested values.
🗝️
Key-Value & Redis-style Structures
String buckets with per-key TTL. Plus lists, sets, and hashes — in-process queues, counters, and coordination primitives with no Redis round-trip.
💾
Four Storage Modes
IN_MEMORY for tests, FILE with WAL recovery for simple persistence, B_TREE for read-heavy apps, LSM_TREE for write-heavy workloads. One flag to switch.
⚡
MVCC Transactions & WAL
Multi-version concurrency control with rollback. Write-Ahead Logging with deterministic fsync durability and crash-restart recovery.

// MVCC transactions — atomic across collections
try (var tx = db.beginTransaction()) {

    tx.documentCollection("accounts")
      .update("acc-1", "balance", 4750.0);
    tx.documentCollection("accounts")
      .update("acc-2", "balance", 5250.0);

    tx.commit(); // both commit, or both roll back
}

Pluggable Storage

    
Four storage modes, one unified API

    
Switch between ephemeral in-memory tests and durable production storage with a single configuration parameter. The query and collection API remains 100% identical.


    

      

        IN_MEMORY
        
Pure Memory

        
Backed by ConcurrentHashMap. Zero disk I/O, microsecond latencies. Ideal for lightning-fast test suites and ephemeral microservice state.

        

          
Throughput:~3.2M ops/s

          
Durability:Ephemeral

          
Disk footprint:0 MB

        

      


      

        FILE (WAL)
        
Append-Only WAL

        
Per-collection JSON snapshots with append-only Write-Ahead Logging. Guaranteed crash recovery upon restart with zero external processes.

        

          
Throughput:~240K ops/s

          
Durability:Full Crash WAL

          
Recovery:Automatic

        

      


      

        B_TREE
        
B+ Tree Indexed

        
Paged B+ Tree indices over persistent records with background checkpointing. Optimized for read-intensive embedded applications and edge nodes.

        

          
Throughput:~480K ops/s

          
Read latency:< 0.2 ms

          
Workload:Read-heavy

        

      


      

        LSM_TREE
        
Log-Structured Merge

        
In-memory Memtables, persistent SSTables, Bloom filters, and background compaction. Engineered for write-heavy telemetry and continuous ingestion.

        

          
Throughput:~720K ops/s

          
Compaction:Level-based

          
Workload:Write-heavy

Integration Guide

    
Framework integration patterns

    
EmbedJNoSQL is a plain Java library — no bytecode agent, no annotation processor, no CDI container needed. Every framework integration follows the same lifecycle contract.


    
    

      
      
      
      
      
    


    
    

      
EmbedJNoSQL is synchronous and in-process. The single rule for Vert.x: never call it directly from the event loop. Wrap with executeBlocking() in route handlers, or deploy as a Worker Verticle for batch/event-bus workloads.


      

        
Pattern 1 — executeBlocking (route handlers)

        
public class ProductVerticle extends AbstractVerticle {
    private EmbedJNoSQL db;
    private DocumentCollection products;

    @Override
    public void start(Promise<Void> startPromise) {
        // ✅ Safe — called once at startup, not on the hot event loop
        db = EmbedJNoSQL.create(EmbedJNoSQLConfig.builder()
            .storageEngine(IN_MEMORY).buildConfig());
        products = db.documentCollection("products");

        Router router = Router.router(vertx);
        router.get("/api/products").handler(this::getAll);
        vertx.createHttpServer().requestHandler(router).listen(8080)
            .onSuccess(s -> startPromise.complete());
    }

    private void getAll(RoutingContext ctx) {
        // ⚠️  executeBlocking keeps the event loop free
        vertx.<List<Product>>executeBlocking(() ->
            products.findAll().stream().map(Product::fromDocument).toList()
        ).onSuccess(list -> ctx.response()
            .putHeader("content-type", "application/json")
            .end(Json.encode(list)))
         .onFailure(ctx::fail);
    }
}

      


      

        
Pattern 2 — Worker Verticle (event-bus / batch)

        
public class DbWorkerVerticle extends AbstractVerticle {
    private EmbedJNoSQL db;

    @Override
    public void start() {
        db = EmbedJNoSQL.open("./data/myapp");
        vertx.eventBus().<JsonObject>consumer("db.products.upsert", msg -> {
            try {
                Product p = msg.body().mapTo(Product.class);
                db.documentCollection("products").insert(p.toDocument());
                msg.reply(new JsonObject().put("status", "ok"));
            } catch (Exception e) { msg.fail(500, e.getMessage()); }
        });
    }
    @Override
    public void stop() { if (db != null) db.close(); }
}

// Deploy as a worker (thread-pool isolated)
vertx.deployVerticle(new DbWorkerVerticle(),
    new DeploymentOptions().setWorker(true));

      


      

        🔷 Vert.x Rule
        EmbedJNoSQL is synchronous. Always wrap calls in executeBlocking() inside route handlers, or use a Worker Verticle for event-bus consumers.
      

    


    
    

      
Javalin handles requests on virtual threads (Java 21+) or regular threads — both are fine for synchronous EmbedJNoSQL calls. Open once, share, close on shutdown.

      
public class Application {
    public static void main(String[] args) {
        EmbedJNoSQL db = EmbedJNoSQL.inMemory();
        DocumentCollection users = db.documentCollection("users");

        var app = Javalin.create().start(8080);

        app.get("/users", ctx -> ctx.json(users.findAll()));
        app.post("/users", ctx -> {
            var doc = ctx.bodyAsClass(Map.class);
            users.insert(Document.of(doc));
            ctx.status(201).json(doc);
        });

        Runtime.getRuntime().addShutdownHook(
            new Thread(() -> { app.stop(); db.close(); }));
    }
}

    


    
    

      
Helidon SE 4 routes run on Java virtual threads — blocking I/O (including EmbedJNoSQL) is perfectly safe without any wrapping.

      
EmbedJNoSQL db = EmbedJNoSQL.open("./data");
DocumentCollection products = db.documentCollection("products");

WebServer server = WebServer.builder()
    .routing(rules -> rules
        .get("/products",
            (req, res) -> res.send(products.findAll()))
        .post("/products", (req, res) -> {
            // Virtual thread — blocking is fine
            var doc = req.content().as(Map.class);
            products.insert(Document.of(doc));
            res.status(201).send();
        }))
    .port(8080).build().start();

Runtime.getRuntime().addShutdownHook(
    new Thread(() -> { server.stop(); db.close(); }));

    


    
    

      
Dropwizard's managed lifecycle makes it easy to open and close EmbedJNoSQL in sync with the application lifecycle.

      
public class MyApplication extends Application<MyConfiguration> {

    @Override
    public void run(MyConfiguration cfg, Environment env) {
        EmbedJNoSQL db = EmbedJNoSQL.open(cfg.getDataDir());

        env.jersey().register(new ProductResource(
            db.documentCollection("products")));

        // Managed lifecycle: Dropwizard calls stop() on shutdown
        env.lifecycle().manage(new Managed() {
            public void start() {}
            public void stop() { db.close(); }
        });
    }
}

    


    
    

      
The universal pattern for any JVM framework — servlet, reactive, or otherwise.

      
// 1. OPEN — once at application startup
EmbedJNoSQL db = EmbedJNoSQL.open("./data/myapp");

// 2. USE — from any thread; the instance is thread-safe
DocumentCollection col = db.documentCollection("events");
col.insert(Document.of("type", "BOOT_UP")
    .add("timestamp", System.currentTimeMillis()));

// 3. CLOSE — on graceful shutdown
Runtime.getRuntime().addShutdownHook(
    new Thread(db::close));


      

        

          
✅ Thread-safe

          
One instance shared across all threads. No pool, no connection manager.

        

        

          
⚠️ Async / event-loop

          
Vert.x / Netty-based frameworks: always dispatch via executeBlocking() or a Worker thread.

        

        

          
🔒 ACID transactions

          
MVCC transactions work inside any thread — including executeBlocking closures.

Design Philosophy

    
Principles, not features

    
EmbedJNoSQL is opinionated about what it refuses to be. Every decision follows from the same constraint: it must run inside your JVM with nothing else running.


    

      

        🚫
        
No Infrastructure Tax

        
No Docker socket, no network port, no daemon, no OS service. The database starts when your JVM starts and stops when your JVM stops.

      

      

        🔍
        
Honest Claims Only

        
Every feature claim has a verified test behind it. Known limitations — power-loss durability, vector search experimental status — are stated plainly, not buried.

      

      

        ☕
        
Pure JVM

        
Three mandatory runtime dependencies: Jackson, SLF4J API. Everything else — Spring, Quarkus, Hibernate — is optional scope. No native libraries, no JNI.

      

      

        🎯
        
NoSQL Only

        
No SQL engine, no JDBC driver, no dual-engine selector. The product is one thing: an embedded multi-model NoSQL database. Stated clearly in every release note.

      

      

        🧪
        
Test-First Reliability

        
1,172 tests passed across the core engine, first-party modules, and demo projects. Maven Central publication and signature verification are in progress.

      

      

        🔒
        
Secure by Default

        
The console HTTP server is opt-in. Authentication, session management, and rate limiting are built in. No console starts unless you explicitly enable it.
