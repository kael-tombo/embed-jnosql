# EmbedJNoSQL Console Feature Inventory

**As of:** 2026-10-15
**Scope:** The shipped static console, its Java HTTP API, sign-in/session flow, and the seeded interactive test fixture. This is an implementation inventory, not a claim that all browser behavior is verified.

## Method and evidence key

The inventory was derived from `src/main/resources/static/index.html` (the rendered panel/control source), `src/main/resources/static/js/console.js` (panel registry, event wiring, API calls, state handling), `login.html` and `js/login.js` (sign-in flow), `EmbedJNoSQLServer.java` (endpoint registration, authentication, CSRF, HTTP handlers), `ConsoleInteractiveTestServer.java` (test fixture), and the focused test run recorded in [baseline.md](baseline.md). Panel inventory starts with `PANELS` and is reconciled against every `section#panel-*` in `index.html`.

Evidence tags:

- **SRC** — behavior/affordance is present in source; this alone does not prove successful browser use.
- **HTTP** — a Java test made a real HTTP request to the embedded server/engine. It does not verify the HTML control wiring.
- **STATIC** — a test asserts asset contents or serving; it does not render the UI.
- **FIXTURE** — seeded/configured by `ConsoleInteractiveTestServer`; fixture setup is not a UI test.
- **UNVERIFIED UI** — no browser-driven acceptance test is present in the baseline evidence.
- **GAP** — source/tests do not establish the described outcome or boundary; verify before claiming it.

The dated baseline records 110/110 passing tests in the selected console test classes. Some feature rows are covered by HTTP-level tests, but the selection does not run browser interactions. No Playwright project/test suite was found in the inspected sources. References to future UI verification are gaps, not implied passes.

## Shared security, state, accessibility, and responsive behavior

### Access and request policy

- The login page posts to `/api/auth/login`. It accepts configured username/password or API key, stores a returned session and CSRF token in `sessionStorage`, and stores a supplied API key in `localStorage`. Empty credential submission is stopped client-side. Failed credentials display an alert; HTTP 429 uses `Retry-After` for a countdown if numeric. A network error is not represented as an authentication result.
- Protected API handlers validate a session cookie, bearer session, or API key when authentication is enabled. Missing/invalid credentials yield 401. With CSRF enabled, `GET`, `HEAD`, and `OPTIONS` are exempt; state-changing requests authenticated with a session need a valid `X-CSRF-Token`. API-key authentication bypasses this CSRF check. The shared `api()` helper adds available session, API-key, and CSRF headers, applies a 20-second request timeout, and distinguishes validation, permission, conflict, rate-limit, backend, timeout, and recovery states. Exact server configuration is deployment-dependent.
- Login is intentionally unauthenticated. Logout is best-effort from the browser; the handler revokes the cookie-associated session when present and clears the cookie. Do not assume that clearing browser storage alone invalidates a server session.
- `ConsoleInteractiveTestServer` configures authentication, CSRF, security headers, brute-force lockout, a loopback listener, and seeded in-memory data. Its source contains fixed test-only credentials and key values; they are intentionally not reproduced here.

### UI state and accessibility

The request helper has explicit idle, loading, success, empty, validation, backend, timeout, permission, conflict, rate-limited, and recovery-required states. Rendering is not uniform: several actions show a badge/error banner, others a toast or raw JSON, and some refresh helpers catch and suppress errors. See per-feature notes below. HTML provides a skip link, named navigation, native form controls, tab semantics, modal roles and labels, and alert/status regions in some flows. The confirmation dialog restores prior focus and accepts Escape; the Help dialog closes with Escape and restores focus to its trigger. **No focus trap is implemented in either dialog, and keyboard/screen-reader behavior has not been systematically verified.** Several field labels are adjacent to inputs without explicit `for` linkage. Keyboard and responsive expectations are therefore requirements for verification, not proof of WCAG conformance.

The existing CSS uses responsive grid/flex rules; the current source includes a narrow-screen topbar-wrap/grid-min-width fix. The previous manual inspection and this baseline do not substitute for a viewport-by-viewport automated test. No feature-specific disabled-state guarantee is inferred unless explicitly noted.

## Seeded interactive fixture

`src/test/java/org/embeddedjnosql/db/console/ConsoleInteractiveTestServer.java` starts an enabled in-memory database, loopback console, auth/CSRF/security-header configuration, and fixed test-only login/key configuration (values omitted). It seeds:

- Document collections `products`, `users`, and `inventory`; `products` receives category and price indexes.
- Simple KV bucket `cache_store`, hash bucket `user_profile_hash`, list bucket `event_stream_list`, and set bucket `system_tags_set`.
- Column family `server_telemetry`.
- No vector seed is created by this fixture, so the initial vector index/empty behavior is exercised unless a test/user creates vectors.

This fixture proves deterministic sample data is prepared by its setup code; it does not prove that browser controls or every backend route were exercised. `ConsoleFeatureValidationTest` also creates an isolated in-memory console per test and seeds additional endpoint-specific data in the relevant cases.

## Explicit verification gaps

1. No browser-driven acceptance test in the recorded baseline verifies any control, navigation, dialog, theme, login page, or responsive behavior.
2. Source/API presence is not a claim that every engine configuration supports every endpoint. The fixture is in-memory and fixed to one local security setup; production engine, filesystem backup restore, Kafka connector, CSRF-failure, rate-lockout expiry, timeout, and recovery states need targeted verification.
3. Theme selection currently defaults to dark and does not validate stored values. `login.html` independently hardcodes dark values. This is the implementation observed, not the approved future light-first expectation.
4. Error states are inconsistent. CDC event fetch failure is rendered as an empty list; Overview audit fetch failure is also treated as empty; some refresh errors are swallowed. Distinguish “empty” from “unavailable” in verification.
5. Confirm the actual semantics of list/set/hash missing keys and empty values, schema strict mode, transaction commit/rollback, restore paths, and vector dimensionality/empty index against handlers and engine-level tests before asserting more than the visible API contract.
6. Accessibility and responsive behavior are partially represented in markup/CSS, not verified end-to-end. In particular, no modal focus trap is present; some labels are not programmatically associated; the topbar Refresh title mentions `R` but no `R` key handler was found in the inspected bindings.
