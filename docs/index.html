Core Philosophy

Built on Five Invariant Pillars

These are architectural constraints enforced across every storage engine and framework starter. A sixth card states the honest boundaries we do not claim.

⚡
Embedded-First, Always
Starts in a single method call and lives completely within your JVM process. No ports, no sockets, no child processes. The lifecycle of the database is the lifecycle of your application.
JunifyDB.inMemory() // 0 network hops
⚙️
Zero Configuration
Fully operational with zero config files, zero environment variables, and zero JVM flags. Every option has a production-safe default. Add durability with one extra method call.
JunifyDB.embed().dataDir("./data")
🔀
Multi-Model NoSQL
Documents, key-value buckets with TTL, Redis-style lists / sets / hashes, and wide-column families share one storage substrate and one lifecycle — a single engine with several data models, not two products bolted together.
db.documentCollection("orders").find(Query.eq("status", "SHIPPED"))
🏷️
Tri-Standard Annotations
JunifyDB transparently reflects Jakarta Persistence (@Entity), Eclipse JNoSQL (@Entity), and Hibernate annotations without adding unwanted compile-time JARs to your classpath.
AnnotationResolver.resolve(Entity.class)
📊
Observable by Design
Every mutation emits a lifecycle event. Built-in atomic metrics counters, Change Data Capture (CDC), and a bounded audit trail (in-memory view with a durable JSONL copy) are active out of the box.
db.events().subscribe(EventType.INSERT)
🧾
Honest Capability Boundaries
JunifyDB is NoSQL only: there is no SQL engine, no JDBC driver, and no relational schema to migrate. Documents are schemaless unless you register validation rules, and a document reference is an id you resolve yourself — never an enforced foreign key. Vectors and the Kafka CDC connector ship as clearly-labeled experimental features.
Documents · Key-Value · Lists/Sets/Hashes · Wide-Column
🧩
Pluggable Storage SPI
Decoupled query and collection layers. Seamlessly toggle between Heap RAM, persistent B-Tree, or high-throughput LSM-Tree with zero application code changes.
.withStorageEngine(StorageEngine.LSM)

One Engine, Several Models

Document and Key-Value, One NoSQL Core

JunifyDB has exactly one execution engine. Documents, key-value buckets, Redis-style structures, and wide-column families are data models on top of the same storage substrate — no second engine to configure, no dialect to keep in sync.

Document
Document Collections
Schemaless documents with native predicates ($eq $ne $gt $gte $lt $lte $in $nin $regex $exists $and $or), sorting, pagination, TTL, and secondary field indexes you can create, rebuild, and drop at runtime.
Best for: flexible schemas, entity mapping, application state, tests
Optional validation rules check documents at insert time. There are no relational constraints: a stored reference is an id you resolve, not a foreign key.
Key-Value & Redis Structures
Key-Value, Lists, Sets, Hashes, Wide-Column
String key-value buckets with per-key TTL, plus Redis-style lists, sets, and hashes and wide-column families — all reachable from the same handle and the same lifecycle.
Best for: caches, queues, counters, session state, coordination primitives
Experimental: HNSW vector search (dimensionality from the first vector), Kafka CDC connector

Shared across every model: the four storage modes below, MVCC transactions, WAL-based recovery, the metrics and event bus, and the embedded Console. Experimental (not production features): HNSW vector search and the Kafka CDC connector — the file CDC connector is fully supported.

Pluggable Core

Four Storage Engines, One Unified API

Choose the durability and access-pattern characteristics for your workload with a single configuration flag. The document and key-value APIs stay identical across all four.

Sub-Microsecond
In-Memory Engine
Non-blocking ConcurrentSkipList & radix maps in heap. Perfect for integration tests and local caches.
Best for: CI unit tests, ephemeral cache
WAL + Checkpoints
File-Based Engine
Binary append-only write-ahead log with background checkpointing; writes replay from the WAL after a crash or unclean shutdown.
Best for: Desktop apps, developer tools
Point & Range
B-Tree Engine
Block-paged B+ Tree on disk with LRU page cache. Optimized for large range scans.
Best for: Embedded transactional systems
Write-Heavy
LSM-Tree Engine
Log-Structured Merge tree with MemTable, SSTables, Bloom filters, and tiered compaction.
Best for: Time-series, telemetry, audit logs
