## Checksum verification — and one honest complication

`sha1sum -c FILE-CHECKSUMS.txt` → **635 OK / 28 FAILED** (663 recorded entries).

The 28 mismatches are **not corruption**. They are the browser-testing evidence files
(`docs/browser-testing/evidence/network/trace-*.json`) that belong to the *other
concurrent session*, which kept rewriting those exact files with new browser runs after
this snapshot's checksum capture. Timeline evidence:

- at capture: `trace-GET-api_health.json` hashed to `d2a28505…`
- hours later: the same file hashes to `7a85b4da…`, while `git status` still shows it as
  modified-but-uncommitted (i.e. its content changed, its commit state did not)
- the captured patch records `index 75fafb5..1f2858f` for that file — a third value,
  because Git blob hashes are not SHA-1-of-content

**Conclusion, stated plainly:** a live working tree under concurrent editing cannot be
pinned by working-tree checksums. The durable baseline is therefore anchored to what is
immutable and provable:

1. **the committed revision** `b10b6cd` (branch pointer + archive) — immutable;
2. **the patch** of the 29 uncommitted files as of capture — a best-effort record of a
   moving target, explicitly labelled as such;
3. **the files themselves**, preserved in place and never touched by this audit.

Per-file checksums remain useful for the 635 committed-and-untouched files (and for
detecting tampering of the committed baseline via the archive).
